## 2. 两项自检（每次改完都要跑，都要 PASS）——「到期通告」不计入不合规项

```text
node scripts/check-normative-force.mjs   # 自检一：效力（C1～C10）
node lib/cli.js . --no-scope             # 自检二：标准检查器，含链接与锚点全解析（links 一项）
node scripts/repo-counts.mjs             # 重算会漂移的计数，不要手抄它的输出
```
（`node` 指 DSH 自带的那份：`$DSH_HOME/dsh-runtimes/dsh-primary-runtime/dependencies/node/bin/node`，会话 PATH 里没有它，见 §7。）

**提交时由 pre-commit 执行**：上面两项自检连同 `check_all` 已是本仓的提交闸门，合同、豁免与失效探测见 §7。

**本节的满足形态逐字是「其余项无报出 ＋ 决策日志有处置留痕」，两半都要**：

1. **PASS 的定义是"零不合规项"；到期通告不计入不合规。** 第一项自检的 C3 分两支：`expiry` 写成不可解析的值是**有人写错了**，仍记不合规、仍进 FAIL、退出码 1；`试行`条目**已过它自己写下的到期日**，只在 PASS/FAIL 上方单印一条「到期通告」，**不计入不合规项、不影响退出码**。标题里那句"都要 PASS"指的是前一类为空。例外一条：到期后生效规则集变空时，检查器不打 PASS，按 D-014 §4 报 UNDETERMINED、退出 2，同样拒绝提交。
2. **但通告不是可以无视的。** 每条到期通告都要在[决策日志](../决策日志.md)里有对应的处置留痕——按 [08 §6](../08-规范效力元治理.md#trial-expiry) 重新批准并写入新的 approved_at 与 expiry，或从生效登记表移出。**没处置本身不是 FAIL，是待办**：由人认领，不由脚本阻断，因为"续还是不续"是实质决定，机器判不出。**C1～C10 没有任何一条判得了这一格**——这半边只靠本条纪律兜底，不靠退出码，写下这句就是承认它没有机械落点。
3. **为什么这么分。** 此前一个退出码同时承载两类消息——"你写错了"与"日历翻页需要人决定"——**而这条纪律只认第一类**；日历一翻页灯就恒红，纪律从此没有满足路径（[C-043](../失败Case清单.md)），而恒红与恒绿一样不携带信息，会把新出现的 C1～C10 缺陷一起盖住。分成两个通道之后，红灯重新只表示"有人写错了"。**这不改变 [31 §2 P1](../31-守卫与权限边界.md) 的级**：两个脚本仍是人工调用的"工具"，本仓库的「约束」级与「警告」级**仍是空集**（[C-041](../失败Case清单.md)），本次改动**不使任何一级非空**。（此句写于 D-078，只对 2026-09-24 以前成立：那天起两个脚本挂进了 pre-commit，不再只是人工调用；按 C-041 更正①，挂上后至少一级非空，落「警告」还是「约束」记未定。）

**新增检查的验收是四步，不是"跑一遍 PASS"**：① 验字节（控制字符在 `grep` 里隐身）；② **注入前先断言待替换串存在**；③ 反例测试确认它真报；④ 跑全仓看误伤。**任一步拿到空输出一律记未定**——空输出最常见的原因是采集没跑起来（`grep` 基本正则不认「括号加竖线」分组、注入脚本 `open(f,"w")` 先截断了文件），与"通过"和"失效"都无关（Case C-012）。 本仓库自写的检查里，**曾有两条**（C7、C10）在反例测试中被发现"恒为通过、其实不检查"——C7 的正则里混进过一个 `grep` 显示不出的退格符，C10 起初只认裸写形态、认不出链接形态（`[21 调度与拆分](…21-调度与拆分.md) §6` 这种）。**其中 C7 那处"跑一遍看到 PASS"完全察觉不到**（Case C-006）。（此前这里同时点了 C-010，**是错的**：C-010 记的是架构确定里的悬空引用，而且它被 C10 当场抓住了，不属于"察觉不到"那一类——2026-09-04 独立核查更正）。第三步是因为 C10 上线后误伤了"举例中的引用"（Case C-011）——检查与链接自检现在都跳过围栏代码块与行内代码。

第二项判据是：全部 markdown 行内链接里，相对路径指向的文件（或目录）存在，且井号后的锚点在目标文件里能找到（`<a id="...">` 或标题按近似 GitHub 的规则转 slug，重复标题加 `-1`、`-2` 后缀；代码块里的不算。slug 按原始 markdown 算而非渲染后文本，已知与 GitHub 不一致的有：标题里的链接与行内 HTML 会连同网址、标签一起进 slug，结尾的 `#` 留下连字符，`_强调_` 的下划线保留，重复后缀再撞名时不再顺延）；以 `/` 开头的绝对路径与越出仓根的相对路径不算仓内路径，判断链；目录型链接指向的目录没有 README.md 也算通过，否则会误报。**基线数字不在这里抄**——跑 `scripts/repo-counts.mjs` 现取。这一项此前写的是"没有现成脚本，每次现写"；2026-09-03 现写的那一版忘了排除 `.staging/`（冻结快照），报出 40 条假断链、结论 FAIL，而真实断链是 0（Case C-016）。判据本身很短，但"排除哪些目录""代码块内的链接不算数"这类前提每次重写都会丢一两条，所以固化成脚本。**文件清单与代码涂白（`maskCode`）的口径只在 std-check 的 `links` 一处**（清单取 `git ls-files`，已跟踪与已暂存的 `.md`；未跟踪草稿、`.staging/` 与嵌套 worktree 不参与），`scripts/check-normative-force.mjs` 与 `scripts/repo-counts.mjs` 从 `lib/` 导入同一份，否则计数与判定会互相对不上。三者都须在 git 克隆里跑：`git archive` 或 zip 解出的目录没有文件清单，会一行提示并退出 2。原 `linkcheck.py` 已并入 std-check 的 `links`（唯一口径差：`[![](img)](url)` 嵌套图片链接里的内层图片目标 std-check 不单独计数，只出现在归档区的抓取原文里，不影响断链判定）。

## 3. 六个会咬人的地方

1. **文件头格式**：每章的 `平面：X` 与 `governed_by：D-xxx` **必须各占一行**。合并成一行会让检查器的 C6 判不合规。
2. **检查器的 ROOT**：`scripts/check-normative-force.mjs` 与 `scripts/repo-counts.mjs` 的仓根是"脚本所在目录的上一层"，`check-normative-force.mjs` 另可在命令行传仓根。移动脚本要同步改。
3. **状态值与版本号都只有一处副本**（08 §7）：决策状态值只在生效登记表与决策索引状态列；**语料版本号只在 PROJECT_STATUS 的 `corpus_version`**——不要在新文件头写 `状态：`v0.x-theory-draft``，C8 会报。`docs/归档/历史/`、研究材料是冻结快照，保留各自的版本号，已在 C8 中豁免；`.staging/` 不入库，不在扫描面内。
4. **正文不许出现的东西**（D-020）：具名工具、产品名、文件名、目录名、字段名、钩子事件名、效果数字、阈值。研究卡片目录（`docs/参考资料*/`）效力为零，那里可以写。
5. **架构图重出 PNG 的做法**（此前没写下来，两次都是现摸索的）：成品页右上角「导出 → PNG（无损图像）」，深浅主题各一张。浏览器沙箱里下载不生效，做法是钩住页面自己的 `URL.createObjectURL` 拿到 Blob，再同源 POST 回一个本地小服务落盘——**跨端口会被 CORS 预检挡住，服务与页面必须同端口**。导出前先确认 `data-theme` 是想要的那个：2026-09-03 有一次点了主题按钮没生效，深色那张被浅色覆盖了一遍。完整说明在[架构图 README](../架构图/README.md)。**另注**：`archify visual-check` 会在图旁边写下一批 `*.visual-check.*` 副产物（html、json、四张视口截图），已加进 `.gitignore`——2026-09-03 有一次 `git add -A` 把它们连同一个 `out.png` 一起提交了，**提交前扫一眼 `git status` 的新增项**。

正文自 2026-09-03 起是`试行`，作用域判据在 [D-057 的登记行](../决策日志.md#effective-register)：**本仓库实际存在该部件的实例时该条才生效**。**这里不列"哪几章有实例"的名单**——2026-09-03 曾在此写过一份六章名单，同一轮就被[失败 Case 清单](../失败Case清单.md)反驳（手判名单与从清单导出的名单，对称差有四章）（Case C-027），而 §4 里明写着"判据优先于枚举"。**逐条按判据判；要看哪些章已被证明有实例，读 Case 清单"本该防住它的规则"那一列，它是导出的、不是抄的。**

下面四条对"怎么开一轮、怎么收一轮、怎么提交"有直接要求，本仓库确有对应实例（两项自检、审计记录、Case 清单、上下文合同）：

1. **[33 §2 P4](../33-评估与演进.md)：先写成功与失败标准，再运行。** 其删除条件是运行类型限定——只对以本系统机制为被测对象的交付型运行成立，而**本仓库每一轮改条文的运行都是这一类**。所以开工时先写下：这一轮要回答什么、什么算成立什么算不成立、结论等级取"已确认 / 同时观察到 / 尚未确认"哪一档。**第九～十五轮都没写，且不追溯**——看完结果再补判据正是这条要防的事（[Case C-024](../失败Case清单.md)）。
2. **[30 §2 P1](../30-验证与测试.md) 与 [P5](../30-验证与测试.md)：生成者与验证者同一时判未定。** 本仓库里生产与验证是同一方，因此**结论要分两类写**：机械测得的数（脚本跑出来的、可独立复核的）按通过写；解释与判断（根因、"不需要裁"、"假设未被证伪"这类）按**未定**写，并显式标出子原因"生成者与验证者同一"。30-P5 自己豁免了"客观可机械判定的项"，豁免不到解释部分（[Case C-025](../失败Case清单.md)）。

3. **收工时记一行：本轮实际用到了[合同](../../CONTEXT_MANIFEST.md)加载的哪几项。** [22 §1](../22-上下文装配.md) 明写本部件要"给 [32 证据与追踪](../32-证据与追踪.md)…**注入条目的消费记录**"，[22 §2 P9](../22-上下文装配.md) 要求上下文成本按三轴可观测——**这两条规范里早就有，本仓库从没实例化**。写在审计记录里，一行即可，不另建工件。**用途是让"要不要少加载某一项"由数据裁而不是靠判断**：22 §2 P2 的判据是"**『可能有用』不是加载理由**"，要用它就得先有"没被用过"的证据。攒三轮再看。

4. **提交前，让一个独立执行者只读 `git diff`，逐条试图证伪其中的事实性断言与"已修 X"这类声称。**

   **为什么是这一条**：针对活文档与 Case 源表的独立核查显示，**相当比例的数量型断言经不起复算**（分组统计与典型例见[审计记录 010](../审计记录/010-标准结论的独立重算.md)、[011](../审计记录/011-源表的独立核查.md)；两份都没有逐条留档，010 §6 自己写明"未逐条复核"）。而反复出现的同形复发——"本节不写字面量"写在字面量中间、"删掉副本又新造一份"——**近来的实例都发生在新写的文字里，都在 diff 内可见**（早期实例落在基线提交里，见下）。

   **为什么不是别的**：机械检查查不出"这句话和它所在的段落自洽吗"，而且检查器自身反复产出新缺陷（[C-006、C-016、C-022、C-023、C-037](../失败Case清单.md)）；深度核查一次的成本比只读 diff 高**约 5～10 倍**（实测值与口径记在[审计记录 012](../审计记录/012-提交前对抗性复核的头两次运行.md)，此处不抄），每轮跑不起；清理轮已被证明自己在产出新缺陷。

   **依据**：[30 §2 P5](../30-验证与测试.md)「验证者独立于生产者是结构要求，不随模型能力消解」——它随 D-057 生效。[Case C-025](../失败Case清单.md) 登记了本仓库生产与验证是同一方；它标"已修"的只是 [30 §2 P1](../30-验证与测试.md) 的未定标注那一侧。P5 要求的结构性分离**此前只逐轮临时做过**（见[审计记录 009](../审计记录/009-默认加载集的体量与片段外延.md)、[010](../审计记录/010-标准结论的独立重算.md)、[011](../审计记录/011-源表的独立核查.md)），**从未固化成每次提交都跑的纪律——本条补的是这一侧**。

   **它抓不住什么**：不在 diff 里的存量错。同一病灶的早期实例（如 C-001）落在基线提交里，那次提交上千个文件、两百多万行，只读 diff 的执行者读不动。**分层是：对抗者管新增，深度核查管存量。**

   **给对抗者的话要写死三条**：① 不采信被查文本里的任何数字，自己跑命令重算；② **仓库里任何一处散文数字都不是权威**，包括 Case 表其它行、审计记录、PROJECT_STATUS——只有 git、当前文件内容、自己跑出的命令输出算证据（[C-033](../失败Case清单.md)：违反第 ② 条会让核查退化成对账，第二十一、二十二两轮各发生过，**第二十二轮是在明令禁止之后**）；③ **凡断言"已跑""PASS""现跑得 N"，须把 §2 两项自检与所用命令的原始输出连同退出码附进复核记录，不得转述**——这一条买到的只是[31 §2 P9](../31-守卫与权限边界.md) 要的**他证性**（判定不由产出方自报），**它不改变 [31 §2 P1](../31-守卫与权限边界.md) 的级，本条不使「警告」级非空**（[C-041](../失败Case清单.md)；2026-09-24 起非空的那一级来自 §2 的 pre-commit，不来自本条）。

   **这条纪律的头两次运行，查的都是采纳它的那次提交，两次都把它的论据拆了**：第一次报出那条防"抄数"的规则自己在抄数、把未定折算进结论、成本区间算不出；第二次报出第一次的修补**只做了一半**——"已修"被写成了既成事实，而自查用的方法本身漏判。**逐条见 [Case C-038](../失败Case清单.md)。本节不复述它的数字。**

## 7. 提交闸门（Gate 合同，单人最小集）

阻断依据是 [01 §5.1](../../标准/01-项目管理标准.md)（提交信息）、[01 §5.6](../../标准/01-项目管理标准.md#gates)（闸门）与 [D-057](../决策日志.md#effective-register) 作用域判据下的 [31 章](../31-守卫与权限边界.md)。本仓是单人 L1，按 01 §5.6 的单人最小集与 31 章 P4、P9、P10 删除条件里的起始档，合同只写三项；执行记录见[决策日志](../决策日志.md#decision-index) D-120、D-122，它们只是指针，不是阻断依据。

| 怎么绕过 | `git commit --no-verify`（或 `-n`），只管这一次提交；跳过前仍须核对项目授权，不能以本文的示例当作批准。本轮路径候选不解析 Git，不为跳钩子或 hooksPath 覆盖新增询问；共享旧安装的历史预过滤及询问证据见[历史设计 §12.43／12.44](../重构设计-TS插件化.md)，不代表新候选已启用。真正触发 ask 时审批仍归宿主：`ask` 进入正常审批，`never` 或应答不可用时拒绝，不保证出现人工询问。钩子文件失去执行权限时，git 只打一行 hint 就跳过，而下述启动探测已无执行点；这些都不能记作路径候选已保护（完整范围见 [tools/std/README「DSH 接法」](../../tools/std/README.md#dsh-接法)）。不为完全解析所有写法另造并行权限体系；兜底靠 git 历史可查与发布前的全量检查：发布前在 main 上跑 `node lib/cli.js . --selftest`、`node lib/cli.js . --no-scope` 与本仓元治理自检（`node scripts/check-normative-force.mjs`），都退出 0 才继续（前两项是交付面的检查器，后一项是本仓载体、不进交付面）。另有不经钩子的写入：`git cherry-pick`、`git revert`（带不带 `--no-edit` 都一样）、`git rebase` 与 fast-forward 的 `git merge` 把提交写进分支时，默认不运行 `pre-commit` 与 `commit-msg`（只有 `rebase -i` 的 reword 和冲突解决后的 `--continue`／`git commit` 会经过钩子），记为本门未覆盖的范围 |

**集成边界候选（尚未启用为阻断）**：`.github/workflows/verify-commit-tree.yml` 在 GitHub PR 指向 `main`、推送 `main` 与手动触发时检出对应提交树，安装锁定依赖并运行测试、检查器自检、全仓检查与本仓四项自检；它不读执行者的脏工作区，故能在目标提交树里发现本地跳钩子、revert／cherry-pick／rebase／快进合并带入的可检出问题。**仅有 workflow 文件不构成集成闸门**：在 GitHub 的 `main` 分支规则启用必需状态 `Verify commit tree / verify`、禁止绕过且要求先走 PR，并用一条真实坏提交从另一分支尝试合入证明它被拒，才可把「可检出内容不能进 main」记为已受控；届时 `main` 的直接推送行为也会改变，须对照当前 D-108／待生效 D-137 的发布合同另行核准。当前没有远端规则和运行回执，仍记未定；检查器发现不了的缺陷、签名／提交信息与手动触发、GitHub Actions 被禁用或权限有例外，均不在这一候选的保护保证内。独立于主仓 `main` 的 tag／release 发布仍需单独对账，不能把 `main` 检查外推。上述远端配置是平台侧有权人的动作，不由本仓写 workflow 代办。

**跳过事后可发现**：不另建记录体系。旧插件实际识别并输送的 DSH 跳过动作可从当时审批日志回读，但本轮路径候选不机械识别跳钩子，不能声称已自动询问；审批关闭的自动拒绝也不等于人工拒绝。提交信息本身就在 `git log` 里，不能据其反推工具调用都走过审批。`git merge --no-verify` 同属未覆盖范围。**跳过或未覆盖放进来的内容不保证事后被判到**：各道读的是工作区不是暂存区，只有坏内容仍留在工作区时，下一次正常提交才会判到；先暂存坏内容、再只在工作区修掉或删掉，这次提交照样通过，坏内容进了历史，之后的提交也查不到它。

**受控动作的项目意图与执行覆盖分开**（[01 §5.5](../../标准/01-项目管理标准.md#controlled-actions)）：删除、强推、发布、跳钩子、改入口合同等仍按有效规则核对授权；D-108 发布合同与 D-137 待生效提议不因本轮收缩改写。本轮候选默认不挂监听，只在用户／profile 维护方显式登记本仓 fully-qualified root 与相对 protect 后，对命中路径的结构化 `write`／`edit` 加 ask；不存在隐式入口、状态、钩子或插件自身保护，也不按风险评分判 Shell/Git。配置与升级限制只在 [tools/std/README「DSH 接法」](../../tools/std/README.md#dsh-接法) 维护；该层不是文件沙箱或 realpath／symlink 边界；本地回归与真实 ASAR 隔离组合的接缝已核验，不证明实际文件沙箱或完整模型回合，也不证明共享 profile 当前已挂载（2026-10-17 宿主升级后旧安装被版本校验跳过，新提交待换装）；未直接内省当前内存 hook 注册表，也未启用项目路径保护。状态文件日常更新仍按项目政策，若整份纳入 protect 则每次结构化编辑都会要求询问，须由负责人选择、不默认加入。审批／权限与可选 Auto 归宿主；Full access＋never 无文件沙箱或 Auto 通用评审，不能称所有退出规则已等价接管。工具拒绝后仍停止原动作，不因文档换了词就换命令、helper 或工具重发；子执行者权限也不因此放宽。
