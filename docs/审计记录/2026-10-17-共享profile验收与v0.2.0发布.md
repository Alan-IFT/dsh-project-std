## 已回读的部署事实

- 当前共享 Desktop profile 的 `package.json` 和 `pnpm-lock.yaml` 将 `dsh-project-std` 锁到本仓本地 Git 提交 `e4caca75c39c84447ff68ae55126cb196c7afd50`；已装包不是 symlink。包内 `package.json` 的 `engines.dsh` 是 `0.2.0-rc.2 || 0.2.1-rc.2`，包版本仍为 `0.1.0`（说明同版本号不能识别本次能力）。已装包的 package、patch、三个入口、CLI、第一份标准技能与该提交的工作树字节 SHA256 相同。
- 新会话的技能目录含 `std-01`～`std-04` 与 `std-templates`；本会话加载标准技能，`std_config {action:'inspect'}` 返回本仓配置及候选路径。这是完整模型回合中的工具调用，不只是 ASAR 隔离组合。
- 用户在 `$DSH_HOME/profiles/desktop/cordis.patch.yml` 为主插件 `dsh-project-std` 加了同 id 完整覆盖：`enabled:true`、`policyVersion:2`，只登记本仓 root 与 `.staging/guard-acceptance.txt`。该路径预置基线 `guard acceptance baseline`。最初会话权限 danger-full-access／审批 never，一次真实 `edit` 返回 `the user rejected tool`，随后 `read` 确认原字节仍在；这是自动拒绝，不是人工点拒绝。
- 用户随后把**同一会话**审批策略改为 ask；只对该测试路径重做一次结构化 `edit`，工具返回成功，`read` 得到 `guard acceptance approved`，用户明确确认在宿主 UI 的该工具审批卡点击了「仅本次允许」。因此本次真实模型回合的 ask → 人工批准 → 文件工具执行 → 字节回读成立；旧 never 拒绝没有换工具绕过。用户最后删除 profile patch 中的整块临时覆盖并重启；只读核到 profile 文件已无同 id 覆盖／测试路径、锁定包仍在且包自带默认 `enabled:false`。本轮创建的已忽略测试文件确认绝对路径与内容后删除。其它 profile 配置未由本仓修改。
