## 冻结接口与前置条件

独立配置治理子插件依赖宿主 tools/fs，技能和旧 opt-in 路径层保持独立；新版 bundle 的配置治理插件默认注册只读审阅和专用受控应用能力（后者仍受当前调用权限／必要审批约束），不修改现用 profile。`enabled:false` 可关闭整项。`protectNativeEdits:false` 默认不改变既有原生编辑行为；维护方明确 opt-in 为 true 后才保护该会话项目根的两个默认配置候选及例外文件，不能由 project.yaml 自行关闭。模型可用专用 `std_config` 工具：

两个候选配置并存时 inspect/review 明示 conflict（本版不提供路径选择参数来绕过冲突；每项事实可分别 inspect 回读），apply 不猜加载器优先级、总是拒绝；旧检查器仍按原优先级，不改变旧兼容语义。既有配置自身无效时不把它当空基线自动修复放行，标 invalid 并拒 apply；先由人修复权威／无效基线。本轮不得悄悄删除另一候选。

- `inspect`：只读，返回项目根、唯一默认配置路径、配置原始 SHA、可用工件候选及来源；候选只表明真实存在，不替项目确认语义。不全仓读正文或运行项目脚本。不存在配置时给明确状态／需模型准备候选，不自动铺目录。
- `review`：只读，完整候选 YAML 文本与当前文件比较，输出 validation、逐项方向／原因、摘要和精确 before／after SHA。无效配置拒收；未知语义绝不当等价。允许缺配置的初始接入提案，但须人审确认基线。
- `apply`：仅通过此工具写项目唯一默认配置或显式 `target:exceptions` 的登记册；参数必须包含候选原文、review 的 before SHA（缺文件用明确 null）与 after SHA。执行前再次校验，非放宽且无未知可正常执行；放宽、混合、首次接入或方向未定必须经宿主单次审批才写。所有应用均须有效 agent／session 项目根；需要审批时，缺服务／无开放 turn／never／拒绝／取消／通道不可用均不写。明确严格或等价的普通路径不新增服务／开放 turn 审批前提，不扫描 session 日志假装通用调用验证。格式错误不能靠批准变成有效配置。

CLI 增加只读配置 review 入口（候选路径明确、输出文本／JSON），不提供脱离宿主的 apply 或‘approved=true’参数。先复用现有 YAML 子集解析与配置验证，提取纯文本校验接口，不增加平行 YAML 语法。未知现有键不改变旧检查器兼容性，但治理工具将其变更判未定或拒收，不能静默丢弃。

## 方向判定

逐字段报告 `equivalent`／`tighten`／`relax`／`unknown`，另有 `invalid`。总体保留各方向标记，不能以若干变严抵消任一放宽／未知。模型的解释不是判定器输入权威，不接受模型传入已算好方向。

- 空白、注释及映射键序变化仅在解析和现有验证成功且值语义不变时等价；声明默认值与缺省虽可能判据同，但证据来源有变化，不能统一剥掉配置当等价。差异地址必须保存键的层级边界（如 JSON Pointer），字面键 `budgets.entry_lines` 与嵌套 `budgets: / entry_lines:` 不得因点连接而合并；未知字段及空容器不得在扁平化时消失。
- 数值预算依实际执行语义：已明示正整数的 entry_lines/stale_days/work_item_stale_days 与四文档上限增大放宽、减小变严；duplicate_min_lines/chars 是重复检测阈值，同样增大放宽、减小变严。缺省、null、可选未声明（可能不检查）或旧值无可比较含义时保守 unknown，不用一个默认算法覆盖所有键；首版不自动判新增预算为收紧（同一工件多角色取最宽预算，新增一项可能改变冲突结论）。
- 首版自动证明仅覆盖上述九种预算的明示正整数变化；`frozen`／`metadata_required`／`tailoring` 等其余变更全部保守 `unknown` 并送审，尚未实现自动集合／裁剪证明。此范围不得宣传为所有字段方向已自动判断。
- 后续扩张必须忠于实际语义：frozen 为整段前缀并集，增加排除范围放宽、减少变严；metadata_required 含整体替换约定及 ! 排除，未声明与 [] 不同；metadata_fields 新增词可能改变日期选择优先级。tailoring 任一匹配 applicable=false 即裁剪，不假设首行覆盖；新增有效裁剪放宽。批准理由的业务有效性不由机器裁决，compatibility.policy 不能凭非空放行。
- tier 上升不预先保证所有检查单调，须核角色要求；证明不足未定。入口/工件映射、docs/work roots、repos、derived、状态词表和 rule_files 都可能改变检查对象、身份或语义，不概括为‘描述事实即正常’；本阶段无法证明单调性的变更判未定并人审。有效纯观察性扩展以后由真实反例决定是否增加自动放行规则。
- exceptions.md 的有效登记会改变退出语义，文本中的批准人不能当宿主批准。本轮支持同一工具 `target:exceptions` 的独立单文件提案（默认 target 为 project）；解析复用现有第一张 Markdown 表登记规则，任何非逐字等价变更统一 unknown 并送审，不自动推断某行已关闭／到期就是安全删除。无效表／登记错误拒收，项目自有例外不由插件决定业务许可。一次 apply 只更新一个文件；配置＋例外必须分次分别 review/apply，不承诺两文件事务或中间态等价。

## 审批与写入边界

专用 apply 在 `execute` 内计算完整 review 后直接调用宿主 `approval.request`（复用正常审计与回答通道），不在 pre-execute 缓存 grant，也不需要 WeakMap 或审批凭证存储。主机通用 pre-execute/guard 仍先执行，任何下游已拒绝／取消都不会进入主体；这不是换工具重试已拒动作。候选原文由该调用不可变参数持有。无 agent、缺失会话根一律无写入；需要审批但无有效开放 turn 或审批异常时无写入；只允许当前调用的 `allowed-once`，不接受模型自报‘人已同意’布尔开关。当前 host rc.2 Auto review 的 allow 不能覆盖下游 ask，宿主负责最终询问通道；approval 服务可组合 human/machine answerer，不能把其 allowed-once 说成密码学真人身份保证。

review 摘要需要把 root、目标、before/after hash、全部非等价字段的实际前后值及原因带入审批 reason（例外提案须可回读原文差异，只有两个 hash 不足以让人判断）；新旧候选各限 32768 UTF-8 字节，完整审批 reason 另限 131072 UTF-8 字节（包含字段转义与文本差异），超过时拒收而非隐去部分变化继续批准；缺字段使用 presence 标记，输出不得依赖 undefined 或非有限数被 JSON 静默转换；参数被工具运行时冻结，应用基于同一调用对象，不接受外部可变候选路径二次读造成批准对象漂移。执行时重读目标 SHA／唯一候选／父目录及文件类型，发现任何漂移停止而非复用旧批准。取消前后复核信号；并发应用同一目标需串行／冲突失败，正常拒绝不创建备份或临时写文件。

写入复用宿主 `ctx.fs` 的 `writeText(target, content, {kind:'replaceIfVersion', version}, signal, sandboxPolicy)`／`createIfAbsent`，原始读后 hash 用于提案并与 stat/read/stat 稳定版本绑定；复用当前 session 的 sandbox policy，不传默认 full-access，也不凭独立 Node fs 绕沙箱。当前官方 fs-local 在每 target 队列临界段核 version 与原子写，fs-sandbox 在每次变更前核当前策略与目标；它们对外部恶意进程的竞争仍不是内核 CAS。准确策略接口已核：`ctx.get('sandboxPolicy').resolve({session: exec.agent.session})`（官方 tool-fs 同用此接口），缺失且 fs 声明有沙箱则 apply 失败关闭；不设提权参数，不为应用配置变更顺便放宽文件权限。外部进程恶意并发及目录换链不能承诺全安全；通过宿主 lstat/resolve/contains 拒绝符号链接出根与非普通文件，宿主 stat 不暴露 link count，因此不承诺完整 hardlink 检测；项目 cwd/root 验证按真实上下文，不信模型任意跨仓 root。缺 root／多配置并存／外部 --config 只允许只读审阅，不自动猜一个写。

已知 native `write`／`edit`／`str_replace_editor` 若直接写受管默认配置或例外，提示使用受控入口（拟拒绝而非重复 ask）；只对该项目确定的配置路径处理，不扩大为全仓冻结。其它工具、Shell／直接解释器、宿主内部与外部写者不由本层封堵，文档不得称全面不可绕过；不新写 Shell 解析。受管工具直接被拒后停止原动作，不把专用入口当绕过已拒授权的路径。正常维护应从一开始用专用入口。

### 真机装机复验（2026-10-16）

用户按本文档装入共享 profile 后，第三个条目 `dsh-project-std-config` 报 “failed to import”。复现根因：`lib/config_plugin.js` 在顶层静态导入了宿主包 `@deepseek-ai/dsh-tools`（用其中的 `defineTool`），而真实 profile 的 `node_modules` 里没有宿主包——已验收的 a035 两个入口都不导入宿主包。隔离 QA 没发现，是因为 harness 把该包显式映射到了 ASAR 副本；那是 harness 的假设，与真机不符。

修复：不再静态导入任何宿主包，直接产出注册就绪的工具定义（`name`/`description`/`parameters` JSON Schema/`output`/`execute`，参数从严校验仍在 `argsOf`）；`schemastery` 继续只用 `createRequire` 探测，且任何不可用情形都只省略挂载期 schema，不再让入口导入失败（申请挂载期 schema 抛错会让整个条目无法激活，而 apply 内校验才是安全依据）。

复验：新增 `test/config-install-import.test.mjs`，在只有本包的临时 `node_modules` 下导入三个入口——这正是真机形态，旧代码会被它直接抓住；QA harness 同时移除了对候选隐藏的 `dsh-tools` 映射，使隔离组合与真机一致。

教训：与安装形态有关的验收必须用真实形态（无宿主包的 node_modules），不能由 harness 提供真机上不存在的解析。
