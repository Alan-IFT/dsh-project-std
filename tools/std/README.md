# tools/std · 标准机械检查

对着 [`标准/`](../../标准/README.md) 里**能机械判定**的那部分做检查，判不了的如实报"未定"。
三态定义、退出码规则、检查器接口在同目录 [CONTRACT.md](CONTRACT.md)；本文只讲怎么用，不复述它。

本工具是 TypeScript 写的 DeepSeek Harness（DSH）插件 `dsh-project-std` 的一部分，运行时只有 Node（DSH 自带的那份），**不依赖 Python，也不要求项目内嵌任何标准副本**。

## 配置治理

`std_config`（`dsh-project-std/config`）是**未安装／未发布候选**，当前共享 Desktop 是已验收的 a035 固定安装、旧路径 guard 默认关闭，不会随此树源码变化。新 bundle 配置入口默认启用，原生编辑保护 `protectNativeEdits:false`；完整接口与限制见 [CONTRACT §10](CONTRACT.md#10-配置治理候选接口)。这不是任意仓库写工具，只认当前 agent/session 的 cwd 及固定治理路径。

在已挂载候选且 tools/fs 注入齐全的独立验证环境，模型从一开始使用专用入口（以下为工具参数，不是 Shell 命令）：

```json
{"action":"inspect"}
```

读取返回的原始配置、hash、validation 及有限工件候选来源；存在不代表角色正确。模型结合项目事实准备**完整替换**文本，例如将已明示的预算从 150 收紧为 140：

```json
{"action":"review","content":"budgets:\n  entry_lines: 140\n"}
```

再用相同 content 和实际 review 返回的 before/after SHA 调用。下面是**仅当旧原文逐字等于 `budgets:\n  entry_lines: 150\n`**时可直接执行的参数；真实项目必须使用自己的 review 结果，首次缺文件 before 明确写 JSON null：

```json
{"action":"apply","content":"budgets:\n  entry_lines: 140\n","before_sha256":"dd705796020c333fd16184b592dc51404129698f68a45c28cf223352025445ef","after_sha256":"fc17311ff1774cbf4008bb3604787b7b13c2e6f658506c037b799695d09982be"}
```

不应为了示例删掉现有其它配置字段；模型应保留完整实际配置。明确收紧／等价不新增审批询问；放宽、未知或首次创建必须取得宿主本次 `allowed-once`，不能传 approved/root/权限字段。例外用三个动作中的同一 `target:"exceptions"`，文本任何变化均送审。无效既有配置、双候选（包括目录／链接占位）拒绝 apply，先由人确认权威；缺 governance 父目录不自动创建。

CLI 是单独只读入口，允许明确指定根外候选（不是项目扫描树），不安装也可从当前编译树运行：

```text
node lib/cli.js config-review D:\projects\example --candidate D:\proposals\project.yaml --json
node lib/cli.js config-review D:\projects\example --candidate D:\proposals\exceptions.md --target exceptions
```

装有相同候选 CLI 的环境可将 `node lib/cli.js` 换成 `std-check`。退出 0 仅表示有效 review 已输出，**不是批准或应用**；无效／错误退出 2。此子命令不接收 --config/--apply/--approved；旧 check/migrate 不接收 --candidate/--target。

可选原生保护由 profile 维护方通过正常宿主配置将第三稳定 id `dsh-project-std-config` 的 `protectNativeEdits` 设 true，不能在 project.yaml 自行关闭。仅拒当前根固定文件的已知 write/edit 及 str_replace_editor 变更命令，read/view 不拦；Shell、外部写者不覆盖。**原工具已拒后停止，禁止自动改走专用工具重试**。本轮不改真实 profile、不安装候选；隔离真实宿主组合已验审批、沙箱与原生保护管线，范围与未覆盖项见设计文档「验收结果」，不等于真实 profile 已安装或人类 UI 已验证。

## 一条命令

在被扫描的项目根执行：`std-check .`（插件包 `bin` 提供；钩子里怎么找到它见下文「提交钩子」）。

标准正文（01～04 章）与模板随插件以技能的形式分发，会话里按需加载；项目里**不放标准的副本**。

退出码：`0` 本次执行的检查全过，或判不了的项**全部登记在案**；`1` 有 FAIL；`2` 没有 FAIL 但有**未登记**的判不了项。
**`2` 不是成功**——把 2 吞成成功，等于把"没检查"记成"检查通过"，而这正是本工具要拦的事。

## 前提

- **Node**：DSH 自带的那份即可（`$DSH_HOME/dsh-runtimes/dsh-primary-runtime/dependencies/node/bin/node`）；不装任何第三方运行时依赖。
- **被扫描目录必须是 git 仓库。** 检查对象来自 `git ls-files`。不在 git 仓库里跑，links 与
  single-authority 会报"git ls-files 退出码 128"并记未定，整体退出 2。这不是工具坏了。
- 项目根有 `governance/project.yaml`（或同名 `.yml`）。配置加载只认这两个路径；换个文件名
  等于没有配置，全部检查一次性记未定。

## 包里有什么、为什么

给装之前想看一眼的人（含收录评审），不展开原理：

- `lib/` 是 `src/` 的构建产物，**提交进 git**。原因：pnpm 从 git 装包默认拒绝执行构建脚本，装入时没有构建步骤；`scripts/check-lib-sync.mjs` 与提交钩子保证它等于 `src/` 的构建结果（设计文档 §4）。
- `lib/selftest*.js`、`lib/core/fixture.js` 是 `std-check --selftest` 的自检夹具，不是测试代码残留：它们造临时目录和临时 git 仓来验证检查器自己，**只写系统临时目录，不写被扫项目**。
- 项目路径层是本轮未发布候选：默认关闭，只对显式登记项目的 `write`／`edit` 结构化路径要求人审；不做通用 Shell/Git 风险判定。它仅加入 `ask` 或弃权，下游的 `ask`／`deny`／`cancel` 原样保留，审批归宿主；配置、升级与未覆盖面统一见下文「DSH 接法」，不据候选文档推断共享 profile 已启用。
- `skills/` 是 `标准/` 与 `templates/` 的正文，由 `scripts/build-skills.mjs` 生成，`check-skills-sync` 保证与源一致；技能由 DSH 的技能服务在会话里按需加载。
- 声明兼容的 DSH 版本（`package.json` 的 `engines.dsh`）只列**实际验证过**的宿主精确版本：`0.2.0-rc.2 || 0.2.1-rc.2`。**0.2.1 起这条会挡路，不再只是给人看的**：宿主在导入插件前按 `engines.dsh`（声明了它时忽略 `peerDependencies`）对运行时版本做 semver 校验（`includePrerelease`，预发布参与比较），不满足就**整包跳过**、插件不挂载，且宿主的安装入口也会先拒绝；旧安装因此会在升级宿主后静默失去技能、`std_check` 与路径层。新增一个宿主版本前，要在这个宿主上用隔离组合实测三个入口都能激活、技能目录与 `std_config` 都在，再把精确版本加进这串；**不写没验证过的范围**（范围会顺带放行其它预发布）。排除方式就是精确版本本身：`0.2.1-rc.3` 这类未验证版本会被拒绝，先验证再改这一行。

## 首跑怎么读

首跑一定不好看。**FAIL 的条数不是质量分**，是"这个项目此前没被这套判据看过"的存量。处置顺序：

1. **先看未定。** 未定多半是配置没填全（缺 `tier`、`layout.work_root` 之类）或对象不存在。
   未定的意思是这项没判成，既不是过也不是不过。先清一批未定，FAIL 那边的图景才可信。
2. **再看 FAIL。** 每条带位置、依据条款、原始证据，照证据复算。
3. **最后看输出末尾的覆盖边界。** 那里逐检查器列"不看：……"，是本次**没有看**的范围，
   不是没有问题的范围。

**不许用 `tailoring` 把红的关绿。** 它的语义是"这条在本项目不适用，理由是……"，粒度是**整个
检查器**，或 `layout` 下的单个工件（`layout:<role>`，见 [CONTRACT §5](CONTRACT.md)）：
写上去之后被裁的那一项变成"不适用"，本来会报的 FAIL 一起消失，不是被修好了（裁掉 `adoption` 时，
`compatibility.policy` 必填一项不可裁剪，照判）。
判"不适用"的判据是**对象不存在**；缺人、没数据、没测试是待确认，不是不适用
（见[如何裁剪并开始使用](../../标准/覆盖与采用检查.md#如何裁剪并开始使用)）。

输出形状（节间空行已略；计数随项目与提交变动，这里不写具体数）：

```
标准检查 · <项目绝对路径>
配置 · governance/project.yaml
登记 · governance/exceptions.md（N 行有效）
  通过 N   失败 N   未定 N（已登记 a · 未登记 b）   不适用 N
失败（N）
  · <一句话> [<路径:行>]
      id：<这条发现的地址>
      依据：<标准条款>
      证据：<可复算的原始摘录>
未定（N）
  · <一句话>
      id：<这条发现的地址>
      原因：<为什么判不了>
覆盖边界（没检查的不等于没问题）
  <检查器名>
    不看：<这次没覆盖到的范围>
结论：FAIL。
```

## 未定项怎么登记

判不了的项可以逐条登记"我看过了，接受到什么时候、谁批的"：在 `governance/exceptions.md`（和
`project.yaml` 同一个目录）的第一张表里加一行，**规则列抄报告里那条发现的 `id`**，再写理由、范围、
批准人、到期（列名按"包含"认，列的顺序和多出来的列都不影响）。登记**不改变结论**——那条仍是未定、
仍逐条列出、仍计入未定计数，变的只有退出码；到期按**运行日**校验，最远写到运行日起 365 天，过期即回到
未登记。**FAIL 不能登记**——那是确定的违规，处置是修；检查器自身出错的未定（`<检查器>/internal-error`）
也不能登记；整个检查器不适用走 `tailoring`。同一张表里项目自己的门号例外（规则列不含 `/`）不参与登记，
但到期照判。表头匹配、关闭的写法、过期／不合格／孤儿行各报什么，见 CONTRACT.md §9。

## 命令行开关

`std-check` 只有这些：

- `root`（位置参数，默认当前目录）：被扫描的项目根。
- `--selftest`：只跑检查器自检，不看项目。这是 CONTRACT.md §3 的**执行点**——改完任何检查器
  都要跑它，退出 0 才算改完。自检不过或没有自检的检查器，其对项目的结论被汇总器作废成未定。
- `--json`：输出 Finding 数组给上层工具消费，退出码规则不变。
- `--no-scope`：不打印覆盖边界。默认输出很长，只想先看结论时用；关掉打印不等于扩大了覆盖。
- `--config PATH`：改从别处读配置。扫只读或第三方项目时用：配置放在被扫项目之外，全程不往
  被扫项目写任何东西。该路径不存在或解析不了一律记未定，不回退去猜项目布局。
- `migrate [root] [--config PATH] [--json]`：只读地输出旧接法迁到本插件的**方案**，不改任何文件。§12.45 修复目标包括已跟踪的普通脚本、CI／任务配置等执行入口，不再只看固定钩子与 Markdown；区分现行执行候选、现行说明、冻结／历史／示例保留项与需判断项，并报告覆盖问题。改不改、怎么改由采用项目与会话模型决定。**源主仓历史验收不是本 branch 的证据；冻结补丁隔离 QA 与当前独立候选身份／接续见仓内 `docs/审计记录/2026-10-11-migrate提交验收.md`。当前候选等待独立复审与正常提交，未安装／未发布；安装版是否具备此能力仍须核对产物身份，版本号 0.1.0 和 CLI 文件在位都不能证明。**

## 版本与发布

**版本号只有一处权威：`package.json` 的 `version`，遵循 [semver](https://semver.org/lang/zh-CN/)。** 发布标签是 `v` 加这个号（`version` 是 `0.1.0`，标签就是 `v0.1.0`）；两处必须一致，不手工对应。

- **打标签前先跑** `node scripts/check-release-tag.mjs v<版本>`。它只读、不打标签、不推送，逐项核对：标签 = `v` + `version` 且是合法 semver；本地与远端都没有同名标签；工作区干净；当前在 `main`；`HEAD` 已推送且等于 `origin/main`。**查不了远端不当作“标签不存在”**，会明确报未通过。
- **升版本号**：先改 `package.json` 的 `version`，提交并推送，再打同名标签。破坏性变更升 MAJOR（`0.x` 阶段升 MINOR），向后兼容的新功能升 MINOR，修复升 PATCH；预发布用 semver 的预发布段（`v0.2.0-rc.1`）。
- **旧日期式标签**（`2026-10-05.1`、`2026-10-10-pre.4` 之类）是迁移期的遗留：保留不动，因为三个仍在用 `git subtree` 的旧项目、以及已装过预发布版本的 profile 锁文件都引用着它们。**新标签一律用 `v` 开头的 semver**；`node scripts/check-release-tag.mjs --list` 能列出现有标签各属哪一类。
- **打标签与推送是对外可见、难以撤回的动作**（别人的锁文件会引用它），由具名的人执行，不由脚本代劳。

## 接入一个项目

**标准与工具随 DSH 插件分发，项目里只放自己的东西。** 采用项目自己写的只有 `governance/project.yaml`（与可选的 `exceptions.md`）；
标准正文是插件提供的技能，检查器是插件的 `std-check` 命令。没有内嵌副本、没有手写的版本声明。

- **安装**（每台机器一次，不在项目里）：`dsh plugin add github:Alan-IFT/dsh-project-std#v<版本>`（例如 `#v0.1.0`），或在 DSH 的 Plugins 页填同一个 git 地址。
  版本标签的写法见下节「版本与发布」；钉哪一版由 profile 的 `package.json` 与 `pnpm-lock.yaml` 承担（机器维护，带完整性校验）。
  **一个 profile 只能钉一个版本**，同一台机器上的几个项目共用它——这是接受的代价（设计文档 §12.33），出现第二个使用者再加“项目可选声明期望版本”。
- **配置**：照实文件抄 [示例项目 `governance/project.yaml`](../../标准/示例项目-连锁零售中台/governance/project.yaml)，字段语义见 CONTRACT.md §5，本文不另立字段表。
  `tier` 是必填的，不写就得到一条未定；`compatibility.policy` 也是必填的（01 §5.3），缺了判 FAIL——兼容策略正文若已有权威位置，这里写一句指针即可。
  四个篇幅预算键 `budgets.status_lines`／`handoff_lines`／`work_item_lines`／`module_lines` 可选：**不声明就不判**，01 §3.7 的 80／60／150／200
  只是参考值（原文：试验参数，不是合格门槛）；声明之后超了判 FAIL，处置是先移出，不是先加预算。
- **升级**：升级是一次显式的 `dsh plugin update`（或重装到新标签），留痕在 profile 锁定文件的 git 历史里。评估材料是**升级前后同一项目的 `std-check --json` 的逐项（`id`）差异**，由工具产生，不由人记。报告自带本次依据的工具与标准内容的摘要（`tool-identity`，CONTRACT.md §8）。
- **从旧接法迁移**：先核对修复产物身份，再在项目根跑 `std-check migrate .`（可加 `--config PATH`／`--json`）。**本工具不替你改项目**；输出退出 0 只表示报告已生成，不表示迁移成功、覆盖完整或可立即删除。**采用项目必须先处理这些调用，否则删除目录后现行检查入口将失效。** 钩子、普通 gate 脚本、CI／任务等 caller 由采用方逐项判断及接入；不因新 CLI 文件存在就删 `.std/`，先解除现行依赖、复核需判断候选及覆盖问题。冻结／历史／审计／示例命中不自动产生改写义务。
  - **接法前提**：确认实际 caller 可取得符合 `engines.node`（`^22.19.0 || >=24.0.0`）的 Node 和钉住身份的 CLI（包的 `bin` 为 `std-check`）。profile 内文件存在不证明重启后的五个 `std-*` 技能可用，也不证明普通终端／CI 已有同一环境；不要硬编码维护者本机 profile。Windows Git Bash 先核 Windows 环境路径转换与含空格整体引用（可用 cygpath 时由采用方验证），缺 Node／CLI 不得静默跳过。
  - **caller 政策不由迁移代定**：保留项目根、参数、wrapper、重定向与原有 0／1／2 处理；2 表示未登记未定，不是成功。历史 pre-push 的 0／2 例外是否保留由采用方判断，不推广到任意自写钩子／脚本／CI。项目其它测试仍需 Python 的选择逻辑不要动。
  - **验收与回退**：在 caller 的真实环境分别验证 0／1／2 及缺 Node／CLI，按原合同观察；同一修复工具／配置／日期迁移前后逐 id、状态及退出码对账，`adoption/compatibility-policy` 不得消失或降级，既有 FAIL／未定不借迁移抹掉。仅合理成对的 links 聚合 PASS 标题变化可说明，历史断链先分析再由采用方决定。保存自己的差异，只回退本轮改动，不用整文件 checkout 丢既有工作。上游修复实施与验收进度以 [设计 §12.45](../../docs/重构设计-TS插件化.md) 为准。
- **提交钩子（新接法默认，不改写迁移 caller 的既有政策）**：把 `std-check` 放进提交、合并或发布的必经路径，退出码非 0 就不放行；退出码 0 已含“未定项全部登记”这层意思，执行层不必自己解释 2。
  钩子里要自己带 node（git 钩子的环境里没有 DSH 的 PATH）。选法与失败关闭的写法见本仓 [`.githooks/pre-commit`](../../.githooks/pre-commit)：
  先试 `$DSH_HOME/dsh-runtimes/dsh-primary-runtime/dependencies/node/bin/node`，再试 `$USERPROFILE/.dsh/` 下同位置（Windows 终端里只有 `USERPROFILE`），再试 PATH 上的 `node`；
  一个都找不到就**拒绝提交并说明缺什么**（失败关闭），不放行也不跳过。这是形态示意，不是发布物。
  `std-check` 启动时先去掉 git 给钩子注入的 `GIT_DIR` 等仓库定位变量，从 git worktree 提交也不会把自检夹具写进被扫仓。
- **报告标准或工具的问题**：到仓库 [`Alan-IFT/dsh-project-std`](https://github.com/Alan-IFT/dsh-project-std/issues) 提 issue，写采用的版本（报告里的摘要或标签）、定位和最小复现；项目侧怎么记见 [01 §8](../../标准/01-项目管理标准.md#adoption)。

### 迁移与工具审批

`std-check migrate` 只有只读的方案输出，没有 `--apply`。它检测插件 CLI 文件在位，**不证明守卫已挂载、审批应答通道可用或迁移已完成**；方案退出 0 也不是迁移成功。执行时按全部现行入口／待判候选及覆盖问题核对→验证 caller→删除旧副本的依赖顺序，逐项审阅、验证与回退，不只处理钩子。方案里的删除、改钩子与 `before.json`／`after.json` 重定向都是写入，不属于读取方案。

审批为 `never` 时，宿主自动拒绝所有触发 `ask` 的动作；这不等于所有普通写入都禁止。可以继续只读盘点、准备差异和验证清单，但**聊天中的“允许继续”不等于工具层批准**。遇到受控动作应停止执行该项，不能拆命令、换工具或改写路径绕过守卫。可由人通过宿主正常权限入口启用审批后在父会话执行，或由人亲自按审阅方案操作并提供差异、钩子正反例和迁移前后逐 id 对账结果；本插件不代替采用项目做迁移决策。

保持 Full access 时，官方 `0.2.0-rc.2` 文档提供的路径是：在正在运行并已登录的 DSH Web 侧栏 **Plugins** 启用 **Auto review**（默认关闭），在当前会话输入 `/permission` 查看可选项，在输入框旁权限选择器选 **Auto review (EXP)** 并确认风险提示；也支持用户显式输入 `/permission auto`。它组合 Full access + `ask`，**reviewer 的 `allow` 不覆盖下游决定**：下游 `ask` 仍走标准审批、须获有效批准；下游 `deny` 保持拒绝，不能靠人工应答改为放行；不在通用设置／未来会话默认值中。Auto 的进程内委派子会话固定 `never`，父会话切换不意味着已创建子会话获得审批。出处：[权限预设](https://unpkg.com/@deepseek-ai/dsh-permission-presets@0.2.0-rc.2/README.md)、[Auto review](https://unpkg.com/@deepseek-ai/dsh-experimental-auto-review@0.2.0-rc.2/README.md)（这两份是 0.2.0-rc.2 的；**0.2.1-rc.2 上未逐条重测**，以本机 `/permission` 列表与实际审批事件为准）。**当前部署是否加载 Auto、具体控件与这条路径的实际行为尚未实测**；以 `/permission` 列表和实际审批事件为准，不要求为此降到只读或工作区权限。

**执行层由采用项目自己接**，标准不发**生效的**钩子、流水线或 agent 侧配置——它们随宿主工具变，上游给一份就会过期成第二处权威；`templates/` 里的 agent、skill 文件是供复制的载体实例，拷进项目的 `.agents/` 之后才生效，由采用方自己决定。插件的项目路径接入契约见下节「DSH 接法」。**发布与效力边界不在本轮改写**：D-108 登记行仍按旧交付面约定，D-137 的取代提议尚未生效（标准仓 `docs/决策日志.md`）；候选职责收缩不自动改变这些约定。
`std-check` 判的是本标准要求的工件与结构，不是 [01 §5.6](../../标准/01-项目管理标准.md#gates) 的 G1–G8；测试、格式、依赖审计各按该节写执行点，可与它并列接进同一钩子。承载可以是版本控制钩子、流水线作业或按清单执行的人工步骤，语义相同。

钩子盲区（都不记为已受控）：`--no-verify` 的提交（git 接受无歧义缩写如 `--no-veri`，`-n` 可并进组合短选项如 `-an`）、`git -c core.hooksPath=… commit` 临时换走钩子目录的提交、钩子文件失去执行权限后的提交（git 只打一行 hint 就跳过），以及 `git cherry-pick`、`git revert`、`git rebase` 与 fast-forward 的 `git merge` 写进分支的提交（这几类默认不运行 pre-commit 与 commit-msg，只有 `rebase -i` 的 reword 和冲突解决后的 `--continue`／`git commit` 会经过钩子）——这些按 [01 §5.6](../../标准/01-项目管理标准.md#gates) 记为该门未覆盖的范围。这些是 **Git 钩子的盲区**，本轮项目路径候选也不解析这些命令、不为跳钩子或 hooksPath 覆盖新增询问；旧安装的历史预过滤行为不是新版保障（见下节「覆盖与宿主限制」）。不为完全解析所有写法另造并行权限体系；兜底靠 git 历史可查与非 fast-forward 合并、发布前的全量检查。非 fast-forward 的 `git merge` 可再接一个 `pre-merge-commit` 钩子（内容为 `exec "$(dirname "$0")/pre-commit"`）转调同一钩子覆盖。

把 2 当告警放行的流水线，其结论不得被引用为"检查过了"。agent 侧的执行点是宿主工具自己的权限规则与调用前钩子，按各工具自己的机制配；没配的按 [01 §5.5](../../标准/01-项目管理标准.md#controlled-actions) 记未定，不记为已受控。DSH 的接法见下节。

## DSH 接法

**这是 DSH 的载体实例，不是标准正文或授权。** `policyVersion: 2` 路径职责收缩已随已验收的 a035 固定包经用户正常入口安装；重启后的技能调用、包身份与默认关闭配置已有证据，不等于路径保护已启用。配置治理是本树新增的已验收但未安装／未发布能力，隔离宿主证据与限制见设计文档「验收结果」。package 暂为 0.1.0，**同号不能识别能力**：切换前核精确 commit、制品／tool-identity digest 与 policyVersion，不自动更新、重装或据文档推断运行中版本。

### 分工与显式配置

标准技能与 `std-check` 仍由插件提供，提交钩子仍按项目自己的质量合同执行；它们不因路径层默认关闭而关闭。接提交钩子前先在项目根跑 `std-check .`、确认退出 0，避免一接入就锁住正常提交；这不授予路径层或发布权限。本候选 bundle 保留 `dsh-project-std` 与 `dsh-project-std-skills`，新增第三稳定 id `dsh-project-std-config`；主插件默认 `enabled: false`、`policyVersion: 2`、`projects: []`，技能和配置入口默认启用，原生治理编辑保护默认关闭。无配置或 disabled 不挂路径监听，没有隐式 AGENTS、状态文件、钩子或插件源码保护。

需要路径人审时，由**用户／profile 维护方在正常配置通道**准备同 id 完整覆盖；以下只是候选示例，不是本轮写入真实 profile 的操作，也不授权 AI 改 profile：

```yaml
- id: dsh-project-std
  name: dsh-project-std
  config:
    enabled: true
    policyVersion: 2
    projects:
      - root: 'D:\Programs\example-project'
        protect: ['AGENTS.md', 'CONTEXT_MANIFEST.md', '.githooks']
```

- 顶层只允许 `enabled`／`policyVersion`／`projects`，项目项只允许 `root`／`protect`；未知键报错，不先投影丢键。`enabled` 必须为布尔值，true 须显式版本 2 及非空项目清单。
- root 须是**当前平台完全限定路径**：Windows 盘符后有根分隔符或完整 UNC server/share，POSIX 以 `/` 起。相对 root、`C:foo`、单根分隔符、残缺 UNC 均拒收；重复、等价或父子重叠 roots 报错，不静默取一项。
- protect 是非空相对路径数组，原形及规整后都不得有空项／空段／`.`／`..`／绝对或根路径；不是 glob。Windows 大小写、段尾点空格、长路径前缀与 ADS 只做声明的词法比较，不证明真实路径隔离。
- 仅会话 cwd 完全限定且位于已登记 root 时应用该项目；相对 `file_path` 按**会话 cwd**解析，不按 root 或进程 cwd 猜。只消费 `write`／`edit` 的结构化路径：等于 protect 或其子路径才 ask，前缀相似不匹配。不相关 cwd、真正越 root 或其它工具原样下游，不跨项目自动套另一项目规则。已启用项目配置但缺有效 cwd，或受管调用路径缺失／空白／类型错误／依赖环境时 ask 说明无法定位；普通相对目标的 `..` 按已确认 cwd 规整。
- 插件先取 `next()`，无本地要求即原样返回；下游 ask／deny／cancel 原样保留，异常传播，**只有下游 allow 才可加入本地 ask**。插件不解释已有批准、不存 grant、不按审批模式自行放行，不做通用风险评分或全局严重度合并。

### 升级与回退

旧主配置顶层 `root`／`protect` 即使为空，或 enabled=true 缺新清单，都明确报迁移错误；旧键仅保留作检测，不能自动清空、过滤或转成默认关闭。schema 与 apply 对完整输入校验；**插件挂载报错不等于工具失败关闭**，宿主若仍运行工具，不能称保护仍在。

因此维护方须先保留原精确包／锁定身份与完整配置，逐项确认原约束、退出覆盖面和新 protect 的选择，再在正常可审批环境验证 schema／挂载、真实结构化写改命中及更严下游保留，之后才切换。失败经宿主正常通道退回原精确包与原配置；不能用相同版本号找回能力，不能借升级重发此前被拒动作。本轮未执行这条升级链。

状态工件的日常更新政策仍属项目；把状态文件加入 protect 会使其所有结构化 write/edit 均要求询问，不能等价表达“只防删除或清空”。**由项目负责人选择是否纳入**，不默认加入、不自动替项目决定规则。

### 覆盖与宿主限制

1. 新层只提出显式项目的结构化路径人审要求，**不解析或新增 Shell/Git 询问**。强推、标签、跳钩子、hooksPath、shell 清空状态、解释器／直接 Node／外部编辑及其它工具未由本层保护；项目原有人审意图不因此取消，仍按有效规则与正常用户授权处理，缺执行点记未定。不要换命令或工具绕过旧安装已拒绝的调用。
2. 这不是文件沙箱、目标侧权限、realpath 或 symlink 防护；cwd/root 的词法范围也不证明跨项目写入被阻止。`std-check` 与钩子只查各自声明的输入：本仓查工作区而非暂存树，未跟踪文件不参与，跳钩子和历史坏内容不保证检出；未接入的 CI 不写成已受控。
3. 沙箱与审批归 DSH。**Full access + never 无文件沙箱，也没有 Auto 通用风险评审**；收到的 ask 自动拒绝，不证明所有风险都被分类。Auto 是可选实验能力，正常入口与子会话限制见「迁移与工具审批」；direct Node 与 PTC outer program 不受 inner review 全覆盖。删除旧启发式不是风险等价迁到宿主，不另造审批、grant 或并行权限体系。
4. 标准 ask 输送／应答缺席与取消的执行结果由宿主负责。`the user rejected tool` 不能单独证明人工点了拒绝；逐调用核 asked.reason、callId、decided.outcome 与有效策略。诊断问题仍是上游交接材料，**本仓未改宿主实现**。`ctx.tools.restrict()` 是可见性过滤，不是安全边界。

**历史证据与当前未定**：DSH 0.2.0-rc.2 上旧版本的隔离安装、技能注册以及 2026-10-10 重启后真实会话询问采纳，保留在标准仓历史设计 `docs/重构设计-TS插件化.md` §12.35／12.36／12.43；未发布旧守卫候选的修复／失败记录保存在源主仓本机冻结回执，不纳入本提交切片，不作为现行使用指导。既有 migrate 修复的提交验收见标准仓 `docs/审计记录/2026-10-11-migrate提交验收.md`，不证明本轮路径层；本切片不纳入其后独立安装续验记录。新配置加载、路径层行为与下游 listener 决定保留已在真实 ASAR 隔离组合中核验；该组合使用 Map-only 工具与最小 session carrier，不证明正常 profile 换装、真实文件工具、完整子会话或模型回合。**0.2.1-rc.2 支持的本轮证据**：用实际 0.2.1-rc.2 ASAR（SHA256 `47874618…`）的隔离组合核到三个入口全部激活、五个 `std-*` 技能注册、`std_config` 注册、路径层对受管目标返回 `ask` 且批准后 body 执行、非受管目标 `allow`、`std_config inspect` 可执行（12/12 检查，见标准仓 `docs/审计记录/2026-10-17-DSH0.2.1兼容与在途收口.md`）；它仍不证明共享 profile 已换装、真实文件工具、完整模型回合或宿主 UI 审批。上述完整集成仍未验收，不能将隔离组合或历史 PASS 折为新候选已安装启用。入口、合同格式及恢复接法仍看标准仓 `docs/附录-载体实例/DSH载体映射.md` 和 [03 §8](../../标准/03-Agent信息获取与上下文管理.md#recovery)，本节不复制宿主应用说明。

## 已知误报形态

- **中文正文里的数值高召回。** 同一个"数字+量词+名词"出现在多个文件就报未定。设计如此
  （同形数字也可能各说各的，机械判不了），不是 bug。逐条登记理由的落点见上文
  「未定项怎么登记」。
- **中文锚点判不了。** 各平台给中文标题生成锚点的规则不一致，工具拒绝猜：中文锚点没匹配上
  记未定，ASCII 锚点才判 FAIL。
- **重复文本的阈值对源码偏松。** 旋钮是 `budgets.duplicate_min_lines` 与
  `budgets.duplicate_min_chars`。**调阈值不是关检查**：证据里会写明用的是项目值还是默认值。
- 重复文本与重复数值这两条判据，只在**一组重复的全部出现位置都落在非文档文件**时才丢弃；丢弃
  的组不静默消失，汇总成一条 `SKIP`（判据不适用，带代表位置），指向 02 §4 按技术债处置。只要有一处落在文档里，照常报。
- **`drift` 的日期判据靠一份动作词表召回。** 日期后 10 字内出现「裁定／批准／已完成」这类词才算
  候选，日期左侧 6 字内出现「复查／到期／下次／计划／截止／保留至／有效期」即丢弃。左侧那一刀是
  实测出来的：`- 复查：2026-12-08（半年）——已复查，无回退。` 右窗口命中「已复查」，而它是计划日
  不是既成事实。换一种写法（词不在表里、或计划词离日期超过 6 字）就漏。命中只产未定，可逐条登记。
- **`drift` 的 ADR 修订判据要求标记词从行首第 0 个字符开始**（剥掉 `>`、`#`、`-`、`*`、`|` 与空白
  之后）。放宽到「前 8 个字符内」时本仓 `docs/` 的候选从 10 行涨到 67 行，全是正文句子
  （`- 只追加地保存原始记录…`、`- 与现有理论：修订 D-027…`）。代价是**换写法即漏**：写成
  「本次修订：…」不命中。围栏代码块（```／~~~，按 CommonMark 开闭：同字符、不短于开围栏才闭合）里的行不看；英文标记 revision／changelog 常作普通名词
  （`revision id "0053_x"`），只在 `#` 标题或后跟冒号／表格竖线／行尾的标签形态才算；「修订后的结论见…」这类
  以「修订后」开头的指代句不算。这三刀都来自采用项目的实测误报。同样只产未定。
- **`drift` 的日期判据以提交时刻在最晚时区 UTC+14 下的日期为基准**，不用提交自带的时区：写日期的人
  与提交者时区未必相同。代价是作者当地时间到 UTC+14 之间那几个小时里写下的提前日期不会被报。
- **`drift` 的工作项载体只认两处**：work_root 直接一层里以该 ID 开头（其后不接数字）的 *.md，或状态源文件里行首的
  `work_item_id：<ID>`。放在 work_root 子目录里的工作项文件不算载体，会报 missing（未定）。

## 已知缺口

- **自检样本自己可能有盲区。** 真实教训：`git ls-files` 曾因 `core.quotepath` 把中文路径输出成
  转义形式，成批产生假 FAIL，而当时的自检是**通过**的——因为样本里的路径全是 ASCII。自检绿
  不等于在你的仓库里也对。新增检查器时，反例样本要包含你项目里真实存在的形态。
- **"§5 的键集合 == 实现读的键集合"目前只能靠人核对，没有机械手段。** 现在两边一致是一次人工 grep
  比对的结果，不是自检保证的；往检查器里加一个新配置键而忘了写进 §5，没有任何东西会报警。
- **篇幅预算不全。** 01 §3.7 六项里 INDEX 一项不执行（「每份文档一行」不是行数）；状态、交接、
  工作项、模块文档四项未声明预算键不判；工作项只看 `layout.work_root` 直接一层、头部带状态字段的
  文件；状态声明为目录时不按 80 行判。
